# lhg-tb-format：多平台排版

> 目标：一份初稿，三平台排版，读者在哪看都舒服。
> 核心纪律：**排版只动皮，不动骨——代码、数字、结论三版必须一字不差。**

## 1. 何时使用

- 初稿已通过自查，要分发到掘金/知乎/公众号时 → 跑本 skill
- 用户只发一个平台时 → 只看第 3 步对应平台的小节
- 用户问"为什么知乎的排版乱了"时 → 查第 4 步差异对照表

## 2. 输入与输出

- **输入**：通过自查的 Markdown 初稿
- **输出**：`draft-<slug>-juejin.md` / `-zhihu.md` / `-mp.md`（按需），每版附带"本版改了什么"说明

## 3. 三平台差异对照表

| 维度 | 掘金 | 知乎 | 公众号 |
|---|---|---|---|
| Markdown 支持 | 完整，原样可用 | 基本完整，站外链接折叠 | 需经编辑器转换，不直接支持 |
| 代码块 | 语言标记高亮正常 | 正常，超长建议折叠 | 用编辑器"代码片段"样式重贴 |
| 站外链接 | 正常 | 折叠/降权，正文只留 1 次 | "阅读原文"只认 1 个链接 |
| 图片 | 正常 | 正常，建议加水印 | 建议 900px 宽，单独上传 |
| 标题 | ≤30 字，标签 3~5 个 | 可稍长，首段决定推荐 | 标题+封面+摘要三件套 |
| 公式 | LaTeX 正常 | 知乎公式语法 | 转图片 |

### 3.1 掘金版

- 标准 Markdown 原样可用，重点检查：代码块语言标记齐全、标题 ≤30 字。
- 标签 3~5 个，从正文技术栈提炼（如 `Python`、`装饰器`、`重试`），不许堆砌。
- 首图即封面：在正文选一张最能代表主题的图，单独列出备选说明。

### 3.2 知乎版

- **链接策略**：知乎对站外链接折叠降权。正文关键链接保留 1 次，文末加一行："完整链接汇总放评论区置顶，欢迎自取。"并提醒用户发布后真的去置顶。
- **超长代码**：>50 行的代码块，正文只留关键行，加一句"完整代码见评论区置顶/源码链接"。
- 数学公式转知乎公式语法，并在旁边标注"已按知乎语法转换"，防止用户二次改错。

### 3.3 公众号版

- **代码块转换**：公众号编辑器不认 Markdown 围栏。输出"代码片段粘贴指南"：每个代码块标注语言，提醒用户在编辑器里用"代码块"样式重贴。
- **小标题密度**：每 300~500 字必须有一个小标题；超长段落必须已拆分（自查 TB-STRUCT-001 应已通过）。
- **文末三件套占位行**（必须显眼标注"发布前替换"，不许混进正文）：
- ``
- ``
- ``

### 3.5 知乎链接处理实例

初稿原文：

````markdown
完整代码见 https://github.com/example/repo，文档见 https://docs.example.com，
讨论见 https://forum.example.com。
````

知乎版改法：正文只留 1 个最关键的，其余收进评论区。

````markdown
完整代码见评论区置顶链接。

---
**评论区置顶**（发布后手动置顶）：完整代码 https://github.com/example/repo，
文档 https://docs.example.com，讨论 https://forum.example.com
````

记住：提示行是写给"未来的你"看的，发布后一定要真的去置顶，否则就是对读者开空头支票。

### 3.6 各平台发布前检查单

**掘金发布前**：

- [ ] 标题 ≤30 字，标签 3~5 个
- [ ] 代码块语言标记齐全（掘金高亮靠它）
- [ ] 首图已选定（正文第一张图即封面）

**知乎发布前**：

- [ ] 正文站外链接 ≤3 个，关键链接已收敛
- [ ] 文末有"链接汇总放评论区置顶"提示行
- [ ] 超长代码块已折叠，正文只留关键行
- [ ] 公式已转知乎语法

**公众号发布前**：

- [ ] 代码块已按"代码片段粘贴指南"在编辑器里重贴（不是截图）
- [ ] 全文搜"占位"，确认无裸奔的占位行
- [ ] 标题+封面+摘要三件套已准备
- [ ] 文末"阅读原文"链接已填（或删除该行）

## 4. 排版通用纪律（所有平台）

1. **标题层级不跳跃**：h1 → h2 → h3 逐级来，不许 h1 直接跳 h3。
2. **中英空格**：中文与英文/数字之间加空格，全文统一。
3. **图片 alt**：每张图写 alt 文本，既是无障碍，也是 SEO。
4. **列表项**：单条 ≤200 字，超了就拆成段落。
5. **行尾空格、连续空行**：清掉，版本控制干净。
6. **内部锚链**：`[回到顶部](#xxx)` 这类链接，锚点必须真实存在，改标题后同步改链接。

## 5. 三版一致性校验

排版完成后，逐项核对（可用插件审计脚本辅助）：

- [] 三版代码块内容逐字一致（diff 检查）
- [] 三版数字、结论一致
- [] 每版单独跑 `tb_audit.py`，blocker 清零
- [] 占位行只出现在公众号版，且标注了"发布前替换"
- [] 知乎版的"评论区置顶"提示行存在

差异只允许在排版层：链接位置、代码折叠、标题长度。事实层有任何差异 → 打回重排。

## 6. 反模式（排版阶段的常见死法）

1. **排版改事实**：为了公众号篇幅删了一段代码 → 不许。宁可折叠，不许删除。
2. **占位行裸奔**：""直接发出去了 → 占位行必须大写加粗标注，发之前全文搜"占位"。
3. **知乎链接裸奔**：正文 5 个站外链接全被折叠 → 按 3.2 收敛到 1 个，其余放评论区。
4. **代码高亮丢失**：公众号粘贴后代码没高亮 → 按粘贴指南用编辑器代码块样式重贴，不许发白底代码截图凑合。
5. **三版各说各话**：掘金版修了个 bug，知乎版没同步 → 修完必须三版重新 diff。
6. **封面图随手抓**：首图和主题无关 → 封面图单独选，和标题一起构成点击理由。
7. **摘要复制第一段**：公众号摘要直接粘正文第一段 → 摘要重写，50 字内讲清"读完能带走什么"。
8. **代码截图凑合**：公众号里贴代码截图而不是代码块 → 截图的代码不能复制，读者会骂。用编辑器代码块样式重贴。
9. **发布时间随缘**：深夜发技术长文 → 技术文适合工作日上午发，读者在"工作模式"时更愿意读干货。
10. **评论区空着**：发完就不管 → 前 24 小时守着评论区，第一个提问的人决定了这篇的口碑走向。

## 7. 自检与反馈

**质检门**：排版输出必须通过——①三版代码/数字/结论逐字一致；②每版审计 blocker 清零；③占位行全部标注"发布前替换"；④知乎版有评论区置顶提示。

**标准冒烟用例**：输入一篇通过自查的初稿，应输出三版文件且代码一致；若某版代码与初稿不一致、或占位行未标注，视为失败。

**一键反馈**：发现本 skill 的问题，以 `[QC] lhg-tb-format <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-tech-blog/issues，正文写清"输入 → 实际输出 → 期望输出"。
