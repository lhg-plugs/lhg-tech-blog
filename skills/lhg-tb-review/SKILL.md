# lhg-tb-review：发布前自查

> 目标：发出去的每一篇，自己敢署名，读者敢照着做。
> 核心纪律：**结论只能是"通过"或"不通过"。"基本没问题"是最贵的一句话。**

## 1. 何时使用

- 初稿写完、排版完成，准备发布前 → 必须跑本 skill
- 用户说"帮我看看这篇能不能发"时 → 按第 3、4 步全量过一遍
- 发布后收到读者"跑不通"的反馈时 → 回到第 4 步第 3 项，先复现，再修

## 2. 输入与输出

- **输入**：待发布的稿件（单文件或目录）
- **输出**：自查报告——机器审计分级统计 + 人工终审六项结论 + 最终"通过/不通过"

## 3. 第一步：确定性审计（机器）

用插件自带的 `tb_audit.py` 扫一遍（40 条规则，零第三方依赖）：

```
python3 <插件目录>/scripts/audit/tb_audit.py --target <稿件> --format text
```

### 3.1 分级处理纪律

- **blocker（必须清零）**：无一级标题、代码缺语言标记、Python 语法错误、示例含真实密钥。修稿件，不许改规则。为清零而改规则算作弊。
- **warning（修或写豁免）**：每条 warning 要么修掉，要么写一句话豁免理由（写进报告，告诉用户）。
- **nit（顺手修）**：花 1 分钟能修的就修，不值得修的忽略，但要在报告里说明忽略了哪几条。

### 3.2 审计报告解读

- blocker > 0 → 直接"不通过"，不用往下看了。
- warning 全是"代码占比过高"这类 → 可能是文章类型问题（如纯代码解析），写豁免理由。
- 同一条 warning 在全文出现 5 次以上 → 说明是系统性问题，修写作习惯，不止修这一篇。

## 4. 第二步：人工终审六项（机器抓不到的）

### 4.1 标题兑现

标题的承诺，在正文前 500 字兑现了吗？

- 标题写"三分钟讲透"，正文 500 字内有没有给出核心结论或可运行示例？
- 没兑现 → 要么改标题，要么把承诺提前。**标题党是取关的第一原因。**

### 4.2 数字出处

逐个检查文中的数字：性能提升、比例、耗时、版本号。

- 每个数字都能说出出处吗（"我本机实测""官方文档 v3.2""论文第 4 节"）？
- 说不出 → 删数字，留定性描述。**编数字是技术写作的红线，一次被发现，长期信任归零。**

### 4.3 代码跑过

- 所有 `python` 示例都真实运行了吗？输出是复制的真实输出吗？
- 没跑过的 → 跑一遍（见 lhg-tb-code 第 5 步），或把"复制就能跑"改成"伪代码示意"。
- 读者说"跑不通"时，先在干净环境复现，再说话。

### 4.4 密钥干净

全文搜索 `sk-` / `password` / `passwd` / `api_key=` / `token=`：

- 搜到的都是占位符（`<YOUR_API_KEY>` 类）吗？
- 有任何一个真实字面值 → blocker，打回。这是安全问题，不是风格问题。

### 4.5 坑真实

"坑"章节的每个坑，问自己三个问题：

1. 这个坑我（或用户）真的踩过吗？
2. 现象、原因、解法三件套齐吗？
3. 没踩过的坑有没有冒充经验？（冒充 → 改成"理论上要注意"并注明）

### 4.6 链接有效

- 所有外链点开看一眼：死链、 example.com 占位链接，全部换掉或删掉。
- 内部锚链（`#xxx`）点一遍，确认标题改名后链接同步了。

### 4.7 十秒快速预检（发之前最后看一眼）

时间不够全量自查时，至少过这 5 条（10 秒）：

1. 标题有承诺吗？前 500 字兑现了吗？
2. 代码块都有语言标记吗？（扫一眼有没有白底代码）
3. 有"运行结果如下"却没贴输出吗？
4. 全文搜 `TODO`，有残留吗？
5. 全文搜 `example.com` / `占位`，有裸奔吗？

这 5 条是读者投诉的高频区，守住它们，至少不会翻车。

### 4.8 读者视角终检（最后 1 分钟）

假装自己是从搜索引擎点进来的陌生读者，问 3 个问题：

1. **3 秒测试**：只看标题+前 100 字，我知道这篇讲什么、跟我有什么关系吗？
2. **复制测试**：随便复制一段代码，能跑吗？（抽查 1 个）
3. **转发测试**：读完我愿意转发给同事吗？如果不愿意，缺的是"坑"还是"结论"？

3 个问题有一个答不上来 → 回到对应章节补。读者视角是最后的校准，别用作者视角自我感动。

## 5. 第三步：输出自查报告

```
自查报告（<稿件>，<日期>）
blocker 0 / warning N（处理情况）/ nit M（处理情况）

1. 标题兑现：通过（承诺在第 X 段兑现）
2. 数字出处：通过（N 个数字，来源…）/ 不通过（<哪个数字没出处>）
3. 代码跑过：通过（A 个示例全部运行）/ 不通过（<哪个没跑>）
4. 密钥干净：通过
5. 坑真实：通过（N 个坑，现象/原因/解法齐）
6. 链接有效：通过（外链 K 个，锚链 J 个）
通过 / 不通过（<原因一句话>）
```

结论只能二选一。不通过必须写清：哪一项、什么问题、怎么改（一句话能改的直接改）。

## 6. 反模式（自查阶段的常见死法）

1. **只跑机器**：审计全绿就直接发 → 机器抓不到"数字编造""坑造假"，人工六项必须过。
2. **豁免成习惯**：每篇都豁免"代码占比过高" → 说明写作习惯有问题，回炉 lhg-tb-draft。
3. **改规则清零**：把"代码占比 60%"改成 80% 来过审 → 作弊，不许。规则是底线，不是 KPI。
4. **结论和稀泥**："基本没问题，建议再看看" → 不许。只能是"通过"或"不通过"。
5. **发完不管**：读者评论"跑不通"已读不回 → 24 小时内复现+回复，修示例或补说明，这是个人品牌的复利。

## 7. 自检与反馈

**质检门**：自查报告必须含——①机器审计三级统计；②人工六项逐条结论；③最终"通过/不通过"二选一；④不通过有改法。

**标准冒烟用例**：输入插件自带的坏 fixture（fixtures/post-bad.md），自查结论必须为"不通过"且 blocker>0；输入好 fixture（fixtures/post-good.md），结论应为"通过"。反例即失败。

**一键反馈**：发现本 skill 的问题，以 `[QC] lhg-tb-review <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-tech-blog/issues，正文写清"输入 → 实际输出 → 期望输出"。
