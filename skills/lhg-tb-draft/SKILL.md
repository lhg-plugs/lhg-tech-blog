# lhg-tb-draft：初稿写作

> 目标：把大纲的要点清单，写成读者愿意一口气读完的正文。
> 核心纪律：**初稿不求完美，但求诚实——没跑过的代码不写"能跑"，没出处的数字不写。**

## 1. 何时使用

- 大纲已确认，要写正文时 → 跑本 skill
- 用户甩来一段写了一半的草稿求续写时 → 先按 lhg-tb-outline 第 5 步反向质检大纲，缺段先补段，再续写
- 初稿已写完、要润色时 → 直接跳到第 5 步反 AI 味

## 2. 输入与输出

- **输入**：确认过的大纲（五段式 + 每章要点）
- **输出**：Markdown 初稿，全文 1500~4000 字，代码块语言标记齐全

## 3. 第一步：开篇（问题段，300~500 字）

### 3.1 钩子三选一

1. **别扭时刻**："每次写到第 5 个 try except，我就想把键盘吃了。"——越具体越好，拒绝"在开发中我们经常遇到"。
2. **反常识断言**："你写的重试逻辑，90% 都可以删掉。"——断言必须在 500 字内用代码兑现。
3. **最小反例**：先贴 10 行"丑代码"，再问"有没有更好的写法"。

### 3.2 开篇铁律

- 前 400 字必须出现"问题/场景/为什么"类锚点词，让读者知道这篇为谁而写。
- 标题的承诺必须在前 500 字兑现（或明确预告"第 X 节给出"）。
- 不许出现"本文将介绍…"这种论文腔，直接讲事。

## 4. 第二步：原理段（机制 > 结论）

### 4.1 写作顺序

1. 先给"核心机制一句话"（大纲里的那句），加粗放段首。
2. 每个关键点按"是什么 → 为什么这样设计 → 不这样会怎样"三层写。
3. 能用比喻就用一个，但比喻只用一次，点到为止，不许为了比喻而比喻。

### 4.2 诚实纪律

- **机制大于结论**："因为每次调用都要重新读权重，所以解码是访存密集型" beats "解码很慢"。读者要的是能迁移的理解，不是背下来的结论。
- **每个断言都要有锚**：性能数字给实测条件，设计取舍给 trade-off，不许"众所周知"。
- 不懂的就写"这部分我没深挖"，比编一段正确的废话强。

## 5. 第三步：实践段（代码是正文，不是附录）

### 5.1 代码讲解纪律

- 每段代码**前**说清目的（一句话：这段代码要干什么），**后**说清关键行（挑 2~3 行解释"为什么这样写"）。
- 代码块前面 3 行没有任何正文引出 = 代码天外飞仙，必须加引出句。
- 示例必须"最小可运行"：删掉所有与主题无关的代码，读者复制、运行、看到结果，三步不超过 5 分钟。

### 5.2 数字纪律

- "提升 x%"、"快 x 倍"、"x 毫秒"这类数字，附近必须有实测条件或来源（"在我本机 M2 / Python 3.11 上实测"）。
- 编不出来的数字 → 删数字，留定性描述（"明显更快"）。**编数字是技术写作里最不可饶恕的事。**
- 版本号、API 名称必须与你实际跑过的环境一致，不许凭记忆写。

## 6. 第四步：坑与总结

### 6.1 坑段写法

每个坑固定三件套：**现象**（当时看到了什么报错/怪事）→ **原因**（为什么）→ **解法**（怎么修的）→ 一句话"如果重来"。

- 坑必须是真实踩过的。没踩过的坑，写成"理论上要注意"并注明，别冒充经验。
- 至少 2 个坑。这是技术文和官方文档的区别：文档告诉你"应该怎样"，博客告诉你"我怎样摔过"。

### 6.2 总结写法

- 3~5 条，每条 ≤30 字，条目化。读者划到文末，30 秒能带走全文。
- 最后给 1 个延伸方向，不多。贪多等于没给。

## 7. 第五步：反 AI 味三板斧（初稿写完必做）

1. **删连接词**：全文搜索"首先/其次/最后/再次/综上所述/总而言之/值得一提的是"，删掉或换成小标题。删了不影响任何信息量的词，本来就不该存在。
2. **拆长句**：平均句长 >45 字的段落，拆成短句。一句只讲一层意思，逗号超过 3 个的句子重点怀疑。
3. **朗读测试**：大声读一遍，读到拗口的地方重写。这是成本最低、效果最好的质检，机器替代不了。

### 7.2 AI 味自查清单（逐条打勾）

- [ ] 全文无"首先/其次/最后/再次"（有 → 换成小标题）
- [ ] 全文无"综上所述/总而言之/值得一提的是"（有 → 删）
- [ ] 没有连续 3 句以相同句式开头（如连续 3 句"通过…可以…"）
- [ ] 平均句长 ≤45 字（超了 → 拆）
- [ ] 没有"不仅…而且…"排比超过 1 次
- [ ] 技术名词第一次出现时给了"人话解释"（如"幂等：多做一次也无妨"）
- [ ] 通读一遍，没有"这句话说了等于没说"的废话句

### 7.3 中文排版细节

- 中英文、中文数字之间加空格（"Python 装饰器"，不是"Python装饰器"）。
- 标题末尾不加标点；一段一层意思，超 400 字的段落拆开。
- 代码里的注释用中文时同样遵守空格规则。

### 5.3 代码讲解"三明治"实例

坏写法（代码天外飞仙）：先甩一句"下面看代码"，代码贴完就翻篇，读者不知道这段代码要证明什么。

好写法固定"三明治"四层，缺一不可：

1. **一句话目的**：这段代码要干什么（如"先看完整可运行的版本，复制到本地就能跑，只用标准库"）。
2. **代码块**：语言标记齐全，最小可运行。
3. **关键行讲解**：挑 2~3 行说"为什么这样写"（如"`@functools.wraps` 保住函数名，调试时不抓瞎"）。
4. **真实输出**：贴真实运行结果，写"运行结果如下"就必须有输出块。

反例对照：

- 坏：`下面看代码：` + 光秃秃的代码块 + 无下文 → 读者：所以呢？
- 好：`先看能跑的版本（只用标准库），关键在三行：` + 代码块 + `三行分别是…` + 真实输出 → 读者：懂了，我也能改。

记住：代码是正文，不是附录。每段代码都值得 3 行以上的讲解，写不出讲解的代码，说明它不该出现。

## 8. 反模式（写作阶段的常见死法）

1. **代码堆砌**：代码行超全文 60%，讲解只有"如图所示" → 每段代码配目的+关键行讲解。
2. **论文腔**："本文将从三个方面介绍…" → 删，技术博客不是毕业论文。
3. **数字裸奔**："性能提升 50%"无任何实测说明 → 补条件或删数字。
4. **伪代码冒充**：用 `python` 标记包装根本跑不通的伪代码 → 要么写成真能跑的，要么注明"伪代码，仅示意"。
5. **虎头蛇尾**：问题段写得飞起，总结段只有"以上就是全部内容" → 总结按 6.2 重写。
6. **术语裸奔**：第一次出现"幂等""闭包"不给人话解释 → 每个术语第一次出现时跟一句 ≤20 字的解释。
7. **自问自答太多**："什么是装饰器？装饰器就是…"连续出现 3 次以上 → 设问是钩子，用一次是巧，用三次是水。
8. **英文术语大小写乱飞**：`python` / `Python` / `PYTHON` 混用 → 语言名首字母大写（Python、JavaScript），命令全小写（pip、npm），全文统一。
9. **"我们"太多**："我们可以看到…我们发现…"满篇都是 → 技术博客的"我们"是作者和读者，"我"是个人的踩坑，"你"是给读者的指令，三者别混用。
10. **结尾喊口号**："让我们一起拥抱开源的未来吧！" → 删。结尾给结论和下一步，不给口号。

## 9. 自检与反馈

**质检门**：初稿必须通过——①开篇 400 字有问题锚点；②数字全部有出处或已删除；③代码块全部有语言标记且有引出句；④坑 ≥2 个；⑤朗读测试通过。

**标准冒烟用例**：输入确认过的大纲，应输出 1500 字以上初稿，五段齐全；若输出无"坑"段、或出现无出处的性能数字，视为失败。

**一键反馈**：发现本 skill 的问题，以 `[QC] lhg-tb-draft <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-tech-blog/issues，正文写清"输入 → 实际输出 → 期望输出"。
