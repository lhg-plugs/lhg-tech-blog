# lhg-tb-outline：选题与大纲

> 目标：把"我想写点东西"的模糊冲动，变成一份"写什么、写给谁、凭什么值得读"的施工图。
> 核心纪律：**大纲是文章的承重墙，墙没砌好就装修（写正文），塌了别怪运气。**

## 1. 何时使用

- 用户说"想写篇博客，主题是 XX"，只有一个技术名词时 → 必须先跑本 skill
- 用户已经写了几段但写不下去、越写越散时 → 回到本 skill 重做大纲，90% 的写崩是大纲崩
- 用户直接甩一篇写完的稿子求润色时 → 跳过第 3 步，用第 5 步反向拆解它的大纲，缺哪段补哪段
- 选题已经非常明确（读者、类型、承诺都清楚）时 → 可跳过第 3 步，直接做第 4 步

## 2. 输入与输出

- **输入**：用户的一句话技术主题（可能只是一个名词，如"装饰器"）
- **输出**：一份大纲，包含：读者定位、文章类型、标题备选 3 个、五段式章节清单、每章 2~4 个要点

## 3. 第一步：选题澄清（最多 3 个问题）

### 3.1 提问原则

1. **一次只问最关键的**：按"读者 → 类型 → 承诺"的顺序问，问完即停。
2. **先开放，后收敛**：先问开放式理解意图，再用选择题帮用户做决定（给 2~4 个选项）。
3. **不替用户做决定**：写给谁、写多深，必须问，不许脑补。
4. **每个问题都要有目的**：答不上来"这个答案会改变什么写作决策"的问题，不问。

### 3.2 必问清单（按需取用，不超过 3 个）

1. **谁读？**——"这篇主要是写给谁看的？（比如：刚入门的新手 / 有经验的同行 / 准备面试的人）"
   → 决定深浅：新手要铺垫，同行要干货，面试者要考点。
2. **什么类型？**——"你想写成哪种？（比如：手把手教程 / 原理解析 / 踩坑记录 / 源码解读）"
   → 决定结构权重：教程重步骤，原理重机制，踩坑重现场还原。
3. **带走什么？**——"读者读完，能动手做出的最小成果是什么？一句话说。"
   → 这就是标题的承诺，也是全文的北极星。答不上来，选题就不成立。

### 3.3 停止条件

- 3 个问题问完，或用户说"就这样，开始吧"，或三个答案都已明确 → 进入第二步。
- 用户中途换主题 → 回到本步重新澄清，不要带着旧大纲硬走。

## 4. 第二步：五段式大纲

技术博客经久不衰的结构是五段式。不是八股，是读者的认知顺序：先被问题抓住，再理解原理，再动手，最后记住坑和结论。

### 4.1 大纲模板

```
# 《标题备选 1 / 2 / 3》（每个 ≤30 字，必须含核心承诺）

## 一、问题（占全文 15%，钩子）
- 场景：读者在哪个具体别扭时刻会点开这篇文章（越具体越好，拒绝"在开发中我们经常遇到"）
- 现状的痛：不用这个方案时，代码/流程丑在哪里（给 1 个最小反例）
- 承诺：读完能带走什么（和标题呼应，前 500 字必须兑现）

## 二、原理（占全文 25%，机制 > 结论）
- 核心机制一句话（能一句话说清的，才算真懂了）
- 需要讲透的 2~3 个关键点（每个点：是什么 → 为什么这样设计）
- 明确不讲什么（划边界，防止写成百科）

## 三、实践（占全文 35%，最小可运行示例）
- 示例目标：跑通后读者看到什么（可验证的结果）
- 环境与前置条件（版本、安装，一句话）
- 关键代码行清单（先列行号级清单，写正文时再展开讲解）
- 运行结果（必须真实跑过，输出贴出来）

## 四、坑（占全文 15%，至少 2 个）
- 坑 1：现象 → 原因 → 解法（必须是真实踩过的，编的坑读者一眼看穿）
- 坑 2：现象 → 原因 → 解法
- 每个坑一句话"如果重来我会怎么做"

## 五、总结（占全文 10%，3~5 条）
- 可带走的结论清单（条目化，每条 ≤30 字）
- 下一步：读者学完可以去啃什么（1 个延伸方向，不多）
```

### 4.2 篇幅分配纪律

- 实践段最长（35%），原理次之（25%），问题/坑/总结三段短平快。
- 全文超过 2000 字才需要二级标题之下的三级标题，否则层级越少越好。
- "坑"少于 2 个 → 大纲不合格，打回。技术文的可信度一半来自踩坑。

### 4.3 标题三备选

每个标题必须回答读者心里的三个问题：这是什么、跟我有什么关系、我能得到什么。

- 好标题公式举例："[技术点]：[它解决的别扭事]"（如"Python 重试装饰器：把 try except 从业务代码里赶出去"）
- 拒绝标题党：标题的承诺必须在正文前 500 字兑现，兑现不了就改标题，不许靠标题骗点击。

## 5. 第三步：大纲质检（写正文前最后一道）

逐条打勾，全勾才能进入正文：

- [ ] 读者定位一句话能说清（说不清 = 写给所有人 = 写给没人）
- [ ] 标题承诺与"问题"段呼应，前 500 字可兑现
- [ ] 原理段有"核心机制一句话"（没有 = 自己还没想透，先想透再写）
- [ ] 实践段示例可验证（跑通后看到什么，能说明白）
- [ ] 坑 ≥2 个且真实（没踩过就去踩，踩完再写）
- [ ] 总结 3~5 条，每条 ≤30 字

## 6. 大纲实例（照着填）

以"Python 重试装饰器"为例，合格大纲长这样：

```
# 《Python 重试装饰器：把 try except 从业务代码里赶出去》
# 备选：《别再复制 try except 了，一个装饰器搞定重试》
# 备选：《重试逻辑写得到处都是？装饰器帮你收束》

读者：会写函数、没写过装饰器的后端新人
类型：教程 + 踩坑

## 一、问题
- 场景：调第三方接口，网络抖动， everywhere 都是 try except
- 反例：10 行"丑代码"（每个调用处复制粘贴）
- 承诺：读完能写出一个通用 retry 装饰器，业务代码零 try except

## 二、原理
- 核心机制一句话：@retry 就是 retry(fn)，调用时先走重试逻辑
- 关键点 1：闭包保存 times/delay 参数
- 关键点 2：functools.wraps 保留函数签名
- 关键点 3：只抓预期的异常，不裸 except
- 不讲：装饰器带参数的三层嵌套以外的奇技淫巧

## 三、实践
- 示例目标：跑通后看到"第 1 次失败…第 2 次失败…ok"
- 前置：Python 3.8+，只用标准库
- 关键行：@functools.wraps(fn) / for 循环重试 / raise 透出
- 输出：真实运行输出贴出来

## 四、坑
- 坑 1：裸 except 把 bug 也吞了 → 现象：程序不报错但结果错 → 解法：只抓 ConnectionError/TimeoutError
- 坑 2：重试无上限打爆下游 → 现象：下游限流 → 解法：次数上限 + 延迟
- 如果重来：第一版就把异常类型参数化

## 五、总结
- 闭包包重试逻辑，参数控制次数延迟
- 只抓预期异常，不裸 except
- 重试只解决偶发失败，不解决必然失败
- 延伸：指数退避（backoff）可以下一期讲
```

注意：大纲里的"坑"必须是你真的能讲出现象→原因→解法的，讲不出的坑位先空着，去踩，踩完再填。

## 7. 反模式（大纲阶段的常见死法）

1. **百科式大纲**：原理段列了 8 个关键点 → 砍到 3 个，一篇只讲透一件事。
2. **无读者大纲**："写给想学 Python 的人" → 太宽，收敛到"写给会写函数、没写过装饰器的后端新人"。
3. **承诺悬空**：标题写"三分钟讲透"，大纲里没有"三分钟能跑通的示例" → 改标题或补示例。
4. **坑位造假**："注意内存泄漏"但自己没遇到过 → 删掉，换成真踩过的，或老实写"没遇到过，但理论上要注意"。
5. **大纲即正文**：大纲里已经写了 500 字正文 → 停，大纲只列要点，细节留给正文阶段。

## 8. 自检与反馈

**质检门**：用本 skill 产出的大纲，必须通过第 5 步的 6 条打勾；缺任何一条都算大纲不合格。

**标准冒烟用例**：输入"写一篇关于 Python 装饰器的博客"，应输出含读者定位、3 个标题备选、五段式章节、≥2 个坑位的大纲；若输出缺"坑"段或标题无承诺，视为失败。

**一键反馈**：发现本 skill 的问题，以 `[QC] lhg-tb-outline <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-tech-blog/issues，正文写清"输入 → 实际输出 → 期望输出"。
