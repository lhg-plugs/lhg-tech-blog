# lhg-tb-code：示例代码规范与校验

> 目标：让读者"复制、运行、看到结果"，而不是"复制、报错、关页面"。
> 核心纪律：**没跑过的代码不许写"复制就能跑"，这是技术博客的底线。**

## 1. 何时使用

- 初稿里要放代码示例时 → 先读第 3 步规范再写
- 写完初稿、发布前 → 跑第 4 步校验流程
- 用户问"这段示例为什么跑不通"时 → 按第 5 步排查清单逐项查

## 2. 输入与输出

- **输入**：初稿中的代码示例需求（要演示什么）
- **输出**：符合"最小可运行"标准的示例代码 + 校验报告（跑通/未跑通及原因）

## 3. 第一步：最小可运行示例四要素

每个示例必须同时满足四条，缺一条就不算"最小可运行"：

1. **完整**：从 `import` 到输出，一个文件能跑。不许出现"前面代码省略""此处接上文"——读者是从搜索引擎直接跳进这一段的，没有上文。
2. **最小**：删掉所有与主题无关的代码。演示重试装饰器就别顺手展示日志系统，一件事一个示例。
3. **可运行**：在干净环境（或注明的前置条件下）真实跑通过。版本号写你跑过的那个，不许凭记忆写。
4. **有结果**：示例后面必须贴真实运行输出。写"运行结果如下"却没贴输出，等于承诺落空。

### 3.1 示例篇幅纪律

- 单个代码块建议 ≤40 行，超了就拆成两段，中间用正文衔接。
- 输出块 >50 行只保留关键行，其余用省略号注明。
- 全文代码行占比超过 60% → 讲解不足，补正文，不许"以代码代讲"。

### 3.2 示例环境声明模板

每个实践段的第一个代码块前面，加一段"环境声明"，模板如下（照着填）：

```markdown
环境：Python 3.11（macOS 实测通过），只用标准库，无需安装第三方包。
```

有第三方依赖时：

```markdown
环境：Python 3.11，需先执行 `pip install requests==2.31.0`（版本号是我实测通过的）。
```

需要外部服务时：

```markdown
注意：以下示例调用真实 API（示意代码），请把 `<YOUR_API_KEY>` 替换成你自己的，
或先用沙箱环境跑通。
```

环境声明的作用：读者跑不通时，第一怀疑对象是"环境不一样"，而不是"你写错了"。
把环境写清楚，能过滤掉一半的"跑不通"评论。

## 4. 第二步：占位符与密钥规范

### 4.1 密钥红线（blocker）

- 示例里出现 `password` / `api_key` / `secret` 等字面值 → **blocker**，必须换成 `<YOUR_API_KEY>` 类占位符。
- 真实密钥一旦发出去，等于公开。写示例时默认"你贴的任何东西都会被爬虫存档"。

### 4.2 占位符规范

- 占位符用 `<尖括号>` 或 `YOUR_X` 风格，如 `<YOUR_API_KEY>`、`https://your-domain.com`。
- 占位符前后 200 字内必须有一句"请替换成你自己的"，否则读者会原样复制。
- 需要外部服务的示例（如调真实 API），必须在正文注明"需替换为你自己的配置"，并标成"示意代码"。

### 4.3 高危命令规范

- `rm -rf` 根路径、`sudo`、格式化、删库类命令，前后必须有"危险/注意"提示。
- 能用安全写法就用安全写法：`rm -rf /tmp/demo/*` 比 `rm -rf /` 好，好一百倍。

## 5. 第三步：校验流程（发布前必做）

### 5.1 静态检查

先用插件自带的 `tb_audit.py` 扫一遍，重点看 TB-CODE-001~016：

- 无语言标记的代码块 → 补上（`python` / `bash` / `js` / `text` 等）
- Python 语法错误 → 修到能过解析
- 括号不配平、围栏未闭合 → 修
- blocker 清零才能进入下一步

### 5.2 动态冒烟（Python）

1. 把每个 `python` 代码块抽出来，按顺序存成独立文件放临时目录。
2. 逐个运行，超时 30 秒，记录退出码和报错。
3. 失败分三类处理：
   - **示例写错** → 修示例，重跑，直到通过。
   - **依赖外部服务** → 降级为"示意代码"，正文注明，不许假装能跑。
   - **依赖第三方库** → 正文必须有安装说明（`pip install xxx==版本号`），版本号写你跑过的。

### 5.3 JS/TS 与 Shell

- JS/TS：有 node 就逐个 `node --check`；没有就只做括号配平检查，并明确告诉用户"未做真实语法校验"。
- Shell：逐行读一遍，确认没有 `rm -rf /` 这类手滑命令；`$` 提示符风格统一（要么全有，要么全无）。

### 5.4 校验报告模板

```
示例校验报告
- 代码块总数 N：python A / js B / bash C / 其他 D
- 真实运行：通过 X，失败 Y（已修复/已标注示意）
- blocker：0
- 未覆盖：<没跑到的示例及原因>
```

## 6. 反模式（示例代码的常见死法）

1. **省略号示例**：代码里写 `...` 或 `# 其他代码省略` → 读者跑不通。要么补全，要么注明"伪代码"。
2. **TODO 示例**：示例里残留 `# TODO` → 这是草稿，不是博客。写完再发。
3. **版本穿越**：用 Python2 的 `print` 语句，却标注 `python` → 现在默认 Python3，对齐。
4. **输出造假**：手写"运行结果"而不是真实跑出来的 → 必须真实运行，复制粘贴。
5. **重复粘贴**：同一段代码在文中出现两次 → 删掉重复，第二次用"如上文代码"引用。
6. **无引出代码**：代码块前面 3 行没任何正文 → 加一句"这段代码做了什么"。
7. **魔法数字**：`time.sleep(0.5)` 不解释为什么是 0.5 → 关键数字给一句注释（"0.5 秒是经验值，太小会被限流"）。
8. **输出与代码对不上**：示例打印 `ok`，输出块贴的是 `success` → 输出必须从真实运行复制，一字不差。
9. **异常示例不给触发条件**："会抛 ConnectionError"但示例里永远抛不出来 → 演示异常处理的示例，必须写出触发异常的代码（如示例里的计数器）。
10. **长导入列表**：示例开头 10 行 import，吓退读者 → 只留示例真正用的，演示用的 import  inline 到函数里也行，注释说明。

### 5.5 校验时机

- 写完初稿后跑一次（修大毛病）。
- 排版三版输出后各跑一次（防止排版改坏代码）。
- 发布前跑最后一次（终审）。

校验越早跑，修的成本越低。拖到发布前夜，一个 blocker 能让你重写半篇。

## 7. 自检与反馈

**质检门**：示例代码必须通过——①全部有语言标记；②Python 示例全部真实运行通过（或已标注示意）；③无真实密钥字面值；④占位符有"请替换"说明；⑤输出块真实。

**标准冒烟用例**：输入含 1 个 Python 示例的初稿，应输出校验报告且示例真实运行通过；若报告写"通过"但示例实际跑不通，视为失败。

**一键反馈**：发现本 skill 的问题，以 `[QC] lhg-tb-code <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-tech-blog/issues，正文写清"输入 → 实际输出 → 期望输出"。
