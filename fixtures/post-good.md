# Python 重试装饰器：把 try except 从业务代码里赶出去

调用第三方接口时，最常见的问题是网络抖动：请求发出去没响应，重试一次往往就好了。很多人的做法是在每个调用处写 try except，时间一长，业务代码里到处都是重试逻辑，读起来很累。

这篇文章用一个 Python 装饰器把重试逻辑抽出来。读完你会得到一段能直接用的代码，以及三个容易踩的坑。

## 原理：装饰器只是语法糖

装饰器的本质是闭包。`@retry` 放在函数上面，相当于执行了 `fetch = retry(fetch)`：原函数被包了一层，调用时先走重试逻辑，再走原函数。

理解了这一点，装饰器的参数、返回值、异常处理就都好理解了：它们都是在 wrapper 里手动安排的。

多说一句为什么用闭包而不是类。闭包写法短，心智负担小，九成的重试、缓存、计时场景都够用。只有当装饰器需要维护复杂状态，或者要在多个方法间共享逻辑时，才值得上类装饰器。先从简单的闭包版本开始，真的不够用了再升级，这是务实的做法。

## 实践：一个能跑的重试装饰器

先看完整代码，复制到本地就能跑，只用到标准库：

```python
import time
import functools


def retry(times=3, delay=1):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            for i in range(times):
                try:
                    return fn(*args, **kwargs)
                except Exception as e:
                    print(f"第 {i + 1} 次失败：{e}")
                    time.sleep(delay)
            raise RuntimeError("重试次数耗尽")
        return wrapper
    return deco


@retry(times=3, delay=0)
def fetch():
    fetch.n += 1
    if fetch.n < 3:
        raise ConnectionError("网络抖动")
    return "ok"


fetch.n = 0
print(fetch())
```

运行结果如下：

```text
第 1 次失败：网络抖动
第 2 次失败：网络抖动
ok
```

`@functools.wraps(fn)` 这一行别漏，它负责把原函数的函数名和文档字符串保留下来，否则调试时看到的全是 wrapper。

## 坑：三个容易写错的地方

第一个坑是裸 except。上面的示例为了演示方便抓了全部 Exception，真实项目里应该只抓你预期会发生的异常，比如网络超时。把异常收窄， bug 才不会被重试逻辑吞掉。

第二个坑是重试无上限。一定要设次数上限，并且两次重试之间加一点延迟，否则下游服务会被你的重试打爆。

第三个坑是幂等性。重试只适用于"多做一次也无妨"的操作，比如下单、扣款这类接口，重试前必须确认服务端做了去重。

## 总结

重试装饰器的核心就三句话：用闭包把重试逻辑包起来，用参数控制次数和延迟，只抓预期的异常。完整代码见 https://github.com/lhg-plugs/lhg-tech-blog，欢迎提 issue 交流。

最后补充一点调试经验。装饰器出问题时，先把装饰器去掉，直接调原函数，确认原函数本身没问题，再把装饰器加回来一层层看。

wrapper 里加一行打印，把每次重试的参数和异常都打出来，九成的问题一眼就能定位。不要在装饰器里藏太多逻辑，它应该是薄薄的一层。

什么时候不该用重试装饰器？如果下游接口不支持幂等，或者失败的原因是参数错误（重试多少次都没用），就别套重试。重试只解决"偶发失败"，解决不了"必然失败"，分清这两类，装饰器才不会背锅。
